# 多 agent 工程协作

以可验证交付为中心，由一个主协调者维护事实、范围和进度。角色表示职责，专业方向写进任务卡；不要为每种框架、终端或产品形态新增 agent 类别。

## 先确定边界

- 读仓库指令、现有计划、相关实现和验证入口。保留现有技术栈、组件及约定，替换需要有任务内理由。
- 区分「用户要求」「已有行为」「建议」「待证假设」。建议和猜测不能自动升级为需求或确定 bug。
- 明确本轮是调查、计划还是实现，以及允许的文件、工具、外部操作。流程不扩大权限：只读任务不改代码，提交、推送和 PR 仅在已授权时执行。
- 多步骤工作给需求稳定编号（如 REQ-01），写可观察验收和非目标；新需求追加编号，变更保留关联。小修复用短任务卡即可，不制造文档工程。
- 主协调者是基线、需求、决策和状态的唯一维护者。复用已有工作文档；临时记录可放 `.codex/work/<task-id>/`，仅用本地 exclude 隐藏未跟踪记录。不要为临时文件改共享 `.gitignore`、取消跟踪现有文件或混入提交。用户要求只读时保留在会话/获准的临时空间。

## 角色与调度

| 角色 | 责任 | 默认能力要求 |
| --- | --- | --- |
| 主协调者 | 定范围、拆片、分配写入权、选模型、裁决冲突、汇总证据 | 综合判断与约束管理 |
| analyst | 盘点事实、复现路径、因果假设及风险 | 盘点可轻量；跨层诊断需更强推理 |
| designer | 决定接口、状态和方案取舍；有 UI 时加入交互视角 | 契约/架构能力，随歧义升级 |
| implementer | 在任务卡边界内实现一个可运行切片 | 机械改动可轻量；复杂生命周期需更强能力 |
| verifier | 设计/执行验证并回报原始结果 | 检查表可轻量；测试设计需匹配风险 |
| reviewer | 独立审查同一稳定修订，给出证据和严重级别 | 不低于被审风险要求 |

首次委派前读 [模型策略](references/model-policy.md)，发现**目标运行环境及账户**实际可用模型、工具和生效配置，由工程内部生成并缓存调度规则，再按任务分配；本 Skill 仅提供策略，不储存中央目录或固定路由。区分工程缓存和单任务覆盖，不回写到分发的 Skill。角色不永久绑定模型；模型能力与 reasoning effort 分开选择。不要把当前云端模型列表当成用户本地清单。

有真实子 agent 工具时使用真实委派；没有时顺序执行这些职责，明确「同一 agent 自审，未完成独立审查」，不假装并行或独立。轻量任务可以合并职责；高风险交付缺少独立审查时保留缺口并由用户决定下一步，不能报告已满足该门槛。Skill 是协作指令；`agents/openai.yaml` 是技能 UI 元数据，都不等于 custom agent 的模型配置，不自动安装 agent 或改用户配置。

按需开人，角色表不是必开名单：

- 从能完成当前切片的最小组合开始；低风险的调查、设计、实现和验证可由同一人先后承担，不能把自审标成独立审查。
- 新增 agent 前明确它能独立产出的结果、依赖是否就绪及写入边界。并行用于缩短独立工作的等待，不为填满并发槽位、凑齐角色或重复同一调查开人。
- 同一任务的追问、补证和修复优先交回原 agent，避免反复重建上下文。任务结束后释放写入权；新任务不沿用无关历史。需要独立审查、上下文已混杂或能力升级时，才带检查点交接给新上下文。

## 上下文与回报

- 委派只传当前目标、验收、约束、基线、依赖和必要事实；其余给可访问的路径/符号/链接与修订，按需读取。不默认复制完整对话、整仓文件、长日志或无关参考。
- 回报先给结论与阻塞，再给改动/位置、验证状态和原始证据位置、未完成项与下一步。保留失败输出及关键片段，长日志留在证据位置；压缩摘要不能丢失权限、反例、风险和待证假设。
- 独立 reviewer 使用未参与方案与实现的新上下文，先读需求、稳定修订和相关原始材料形成判断，再对照作者说明。不先灌入作者自评或上一轮结论；相关原始证据必须可访问，不能只给协调者摘要。复审已有问题时再提供问题清单和变更差异，保留同一修订的证据链。

## 执行闭环

1. **建基线**：记录修订、可复现现状、需求与验收。研究阶段结束于发现/建议，不顺手实施。
2. **拆切片**：每片尽量能单独运行和验证。使用 [任务卡](references/task-cards.md) 写明依赖、证据、预算及升级条件；只有依赖已满足且逻辑独立的任务可以并行。
3. **控制写入**：每个文件/模块/共享契约同一时刻只有一个 writer。只读调查可以并行。worktree 隔离文件系统，不会消除逻辑冲突；协调者先裁决契约变更再接入下游。
4. **设计后实现**：复用既有路径，先最小端到端闭环，再扩展。不要让下游基于尚未确认的接口大面积开工。
5. **验证与独立审查**：冻结一个可标识的修订，verifier/reviewer 读取同一基线。采用下方质量视角并只加载相关参考；修复后换新修订，重验受影响证据，不能把旧版通过结果当作新版通过。
6. **采纳与修复**：审查项分 Blocker（不能交付）、Important（实质正确性/验收风险）、Polish（可选改进），必须带位置、复现/推理证据和影响。主协调者裁决互相矛盾的意见，记录采纳清单和拒绝/延期理由。默认最多两轮修复再审；仍有 Blocker/Important 时停止重复试错，先按下方会诊规则诊断根因并报告阻塞，不直接开始第三轮机械补丁。拆片或会诊不重置预算，继续实现需明确新的计划与获准预算；不能降低验收标准或把问题改名为 Polish。
7. **交付**：按「需求 → 实现/修订 → 证据 → 状态」回报。区分已实现、已验证、待验、阻塞及获准延期，不把代码存在当成功。提交前检查仅含授权文件；已授权 PR 时提供链接、精确提交及对应检查结果。

## 按需专家会诊

- 跨层状态/生命周期、安全或公共契约的关键决策存在高影响歧义时，在扩大实现前请相应领域专家评估；同类故障反复出现、修复来回推翻或原假设被证伪时，先定位根因再继续，不必等耗尽两轮。
- 会诊是有边界的临时任务，可由具备领域能力的 analyst/designer 承担，不新增常驻必开角色，也不因触及某领域就自动升级。提供一个明确问题、候选方案、已尝试内容、约束和原始证据；默认只读，输出根因/取舍、依据、不确定性与最小验证建议，由协调者裁决。
- 按模型策略选择实际可用且胜任的能力；专家不等于固定型号或最高 effort。权限、环境或缺失证据的问题先处理相应阻塞；会诊仍受剩余预算和授权边界约束，超出时先申请，不能无限重试。
- 参与方案或修复的专家不能替代该方案的最终独立 reviewer。会诊建议仍需实现后在稳定修订上验证与独立审查；专家不可用时保留风险/阻塞，不把未验证建议当结论。

## 质量视角：按风险选择，不按产品派生角色

所有工程按相关性检查：行为与契约、数据/状态不变量、资源与进程生命周期、失败恢复、兼容性、安全/隐私、性能。CLI、后端、桌面、库、插件及音频都可用这些视角。无 UI 时不强加视觉任务。

有 UI 时增加真实渲染与交互验证：主路径、空态、加载、错误、重试、焦点/键盘、窗口或布局边界；截图只证明画面，不能证明逻辑或真机集成。设计意见要对应需求或可复现问题，不按个人审美无限返工。

验证必须写 `passed / failed / skipped / unrun`、环境、修订和证据。区分 mock 与真实集成、开发浏览器与实际打包运行时、模拟设备与真机。缺少设备/权限/构建能力时保留待验项和下一步，不声称已经听到声音、拍过截图或通过真机测试。
