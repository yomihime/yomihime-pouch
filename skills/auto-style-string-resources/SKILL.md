# Auto Style String Resources

## 目标

用于在当前仓库内整理和风格化程序字串：先审计字串资源、硬编码 UI 文案和调用上下文，再从用户输入、README、docs、现有高质量字串和真实使用场景中归纳目标风格，最后按 `style_score` 和处理等级提出候选改写，并只在用户确认的范围内分批应用。

这不是普通代码重构。默认目标是提升文案一致性、可读性和项目气质，同时保护流程说明、警告、数据风险提示、编译/导出说明、错误信息、占位符和运行时契约。

## 默认行为

- 用户只说“整理字串”“统一文案风格”“风格化 UI 文案”时：只做审计、归类、`style_score`、处理等级和 before/after 示例，不直接修改文件。
- 用户说“自动处理低风险项”时：只修改低风险且明确标记为“可自动改写”的字串。
- 涉及关键引导、费用/API Key、素材清理、隐私、文件覆盖、导入/导出、编译、知识库结构、错误恢复、模型调用、路径/命令/错误码、配置或持久化语义时：必须先给候选并等待用户确认。
- 多语言文案默认只展示用户当前交流语言对应的 locale；用户明确要求跨语言审计、翻译同步或指定 locale 时，才展示其他语言。当前仓库中简体中文通常对应 `zh_CN`。
- 每轮只处理一个清晰批次；不要顺手混入 UI、逻辑、布局、架构、数据结构或依赖改动。

## 信息来源

按优先级读取并交叉验证：

1. 用户本轮给出的风格示例、禁忌和取舍。
2. 当前调用位置和功能语义，包括按钮、空状态、提示、警告、错误、状态、弹窗、导入/导出、编译和预览流程。
3. `README.md`、`ARCHITECTURE.md`、相关子目录 `ARCHITECTURE.md`、`docs/reference/product-design-guidelines.zh_CN.md` 和稳定参考文档。
4. 现有较高质量字串，但不要把所有旧字串默认视为正确风格。
5. i18n 资源与对应 UI 使用位置；默认先看用户语言，其他语言只作为用户要求时的补充核对。

如果文档、代码和现有字串互相冲突，说明冲突并以当前代码和真实调用链为准。

## 工作流

### 1. 扫描字串

优先使用 `rg` 定位，不写脚本作为默认前置条件。至少覆盖：

- `i18n/*.json` 中的用户可见文案。
- `gui/**/*.py` 中的标题、按钮、Label、ToolTip、InfoBar、MessageBox、占位符、空状态、菜单、Tab、状态文本。
- `core/**/*.py`、`utils/**/*.py` 中传入 UI、洞察流、导出物、错误展示、用户可见报告的文本。
- prompt、Markdown/HTML 模板、导入/导出格式说明中会直接呈现给用户或外部系统的文本。

扫描时区分“用户可见文案”和“技术字串”。不要把配置键、JSON schema 字段、持久化字段、测试断言、日志分类、命令片段、路径模板、错误码和协议字段当成普通文案处理。

### 2. 构建 UI/UX 字串树状图

先输出 UI/UX 字串树状图，而不是马上改写。树状图描述字串在用户体验中的使用位置，不是源码目录树。按“页面 → 分组/区域 → 控件/流程 → 词条”分层，让用户看见每条文案属于哪个界面、哪个操作路径、哪个显示场景。

节点命名优先使用用户能理解的 UI/UX 概念；可在叶子条目附带类名、文件、行号或 i18n key 作为定位信息。不要把 `gui/core/utils/i18n` 目录直接当作树的主结构，除非当前字串没有明确界面归属，只能暂放到“后台流程”或“派生产物”分支。

如果使用 `scripts/draft_string_tree.py`，它的输出只能作为 AI 内部草稿。正式给用户看的树状图必须经过 AI 重整：合并重复 locale/key、改成真实 UI/UX 层级、隐藏无关源码噪音、只保留用户语言，并把不确定归属项单独标为“待确认”。

建议树形：

```text
CharaPicker UI/UX strings
├─ 首页/项目页
│  ├─ 素材导入
│  │  ├─ 主按钮：导入素材 [i18n] key=... file=...
│  │  └─ 空状态说明：尚未添加素材 [hardcoded] file=...:line
│  ├─ 素材处理
│  │  ├─ 进度状态：正在处理第 N 个文件 [placeholder]
│  │  └─ 风险提示：清理 raw/ 前确认 materials/ 可用 [protected]
│  └─ 洞察流
├─ 角色卡页
│  ├─ 海报墙
│  ├─ 创建/编辑弹窗
│  ├─ 封面裁剪
│  ├─ 编译/重编译
│  └─ 导入/导出
├─ 模型页
│  ├─ 模型预设
│  ├─ API Key
│  └─ 连接测试
└─ 后台与派生产物
   ├─ 角色卡 Markdown/HTML
   ├─ Character Card V2 JSON
   └─ AstrBot 手动复制清单
```

每个叶子条目用紧凑标签记录：UI 场景、控件/状态/弹窗类型、key 或行号、当前文本、`i18n`/`hardcoded`、多语言覆盖状态、占位符/插值、Markdown/HTML、快捷键、路径/命令/错误码、是否疑似技术字串。不要在树状图里写长解释；把需要讨论的项另列到候选表。

### 3. 归纳目标风格

先从样本中归纳，不预设所有旧文案都正确。输出简短风格原则，至少包括：

- 语气：清晰、轻微拟人化但不牺牲准确性；高风险场景直白。
- 信息密度：短控件文本简洁，流程说明保留必要条件和后果。
- 项目气质：贴合 CharaPicker/拾卡姬 的角色档案、素材洞察、Extract Once、Visible Thinking 等产品方向。
- 禁区：不能为了可爱、口语化或统一长度而削弱警告、费用、密钥、素材清理、覆盖、导出兼容、知识库事实来源等信息。

如果用户提供了示例，优先从示例抽象风格规则，并说明哪些规则来自用户、哪些来自仓库。

### 4. 打分与处理等级

不要再为每条字串做“三个维度 + 低/中/高 + 逐条理由”的长评估。逐条记录只保留一个参考分数和一个处理等级。

参考分数使用单轴“可风格化程度”：

- 记为 `style_score`，范围 `0.0` 到 `10.0`，步进 `0.1`。
- `0.0` 表示最标准化：应保持中性、准确、契约式表达，通常不适合拟人化或风格化。
- `10.0` 表示完全风格化：可以明显承载项目语气、节奏和角色感。
- 分数只作为排序和讨论参考，不等于自动修改许可。
- 逐条表格中不要解释分数；只给数字。只有争议项、保护项或用户要求时，才在单独说明区补充简短原因。

处理等级仍按上下文风险决定：

- 可自动改写：语义明确、技术约束少、`style_score` 较高或中高，通常是按钮、短标题、空状态短句、普通成功提示。
- 只给候选：语义重要或上下文稍复杂，可以提出 before/after 供用户选。
- 默认保护：高风险警告、密钥/费用/隐私/删除/覆盖/迁移/编译/导出兼容等文本，除非用户明确确认，否则不改；这类文本通常 `style_score` 较低。
- 只整理不改写：结构上需要迁移到 i18n、补全多语言或建立索引，但原文不应在本轮改变。
- 需要用户确认：风格方向、术语取舍、跨语言一致性或业务语义存在不确定性。

### 5. 生成审核样本

正式改文件前，必须先给用户看不同处理等级的 before/after 示例。示例应覆盖：

- 低风险可自动改写项。
- 中风险候选项。
- 默认保护项及必要说明。
- 只整理不改写项。
- 需要用户确认的术语或语气取舍。

每个示例包含：位置、场景、当前文本、候选文本、`style_score`、处理等级、保留的占位符/格式约束。不要为每条示例写长理由；只在保护项、争议项和需要用户确认项旁边补一句必要说明。

### 6. 分批应用

只有在用户确认范围后才改文件。应用时：

- 严格限定在确认的文件、key、页面、模块或风险等级范围内。
- 保留所有占位符、插值变量、格式说明符、转义序列、Markdown/HTML 标签、快捷键标记、路径、命令、错误码和外部格式字段。
- i18n 修改要维护四语 JSON 的 key 对齐；如只能可靠改一种语言，明确说明其他语言保持不变或需要后续人工确认。
- 硬编码 UI 文案若适合迁移到 i18n，先把迁移列为“只整理不改写”或单独候选，不在文案风格批次中顺手改调用结构。
- 不调整控件结构、布局、信号槽、业务逻辑、线程、导出字段映射或知识库结构。

### 7. 验证与汇报

修改后输出：

- 已改文件和范围。
- before/after 清单。
- 每项 `style_score`、处理等级和必要说明；常规低风险项不逐条写理由。
- 跳过项及原因。
- 已知风险和仍需确认的文案。
- 运行过的验证命令和结果；至少进行 JSON 解析或相关轻量检查。若无法运行验证，说明原因。

如改动影响长期文案规范、术语或 i18n 工作流，建议是否更新普通项目文档；不要擅自修改 `AGENTS.md`。

## 输出格式建议

审计阶段使用表格或紧凑分组：

| 位置 | 场景 | 当前文本 | style_score | 处理等级 | 建议 |
| --- | --- | --- | --- | --- | --- |

应用后使用更具体的 before/after：

| 位置 | Before | After | style_score | 处理等级 |
| --- | --- | --- | --- | --- |

表格过长时，按页面或风险等级拆分，并把完整清单写入用户确认的临时审计文档；不要把大型一次性清单塞进 `AGENTS.md`。

## 可选工具脚本

脚本只用于辅助初筛和约束检查，不能替代人工理解调用上下文。运行脚本后仍要回到真实 UI/UX 场景中整理树状图、判断处理等级和生成候选改写。

- `scripts/draft_string_tree.py`：粗扫 `i18n/*.json` 与 `gui/`、`core/`、`utils/` 中常见 UI 调用字串，输出 Markdown 或 JSONL 草稿。它会用文件名、i18n key 和常见控件调用推断页面/分组，只能作为树状图起点；正式提交给用户前必须由 AI 重整成页面 → 分组/区域 → 控件/流程 → 词条的 UI/UX 树。使用 `--locale` 只扫描用户语言；只有用户要求时才重复指定多个 locale。
- `scripts/check_string_constraints.py`：比较 before/after 是否保留 `{placeholder}`、`%s`、`$name`、HTML 标签、Markdown 链接、快捷键、路径和错误码等约束。用于候选改写前后自检；脚本报错时优先保护原字串。

示例：

```bash
python .codex/skills/auto-style-string-resources/scripts/draft_string_tree.py --root . --format markdown --locale zh_CN --max-entries 80
python .codex/skills/auto-style-string-resources/scripts/draft_string_tree.py --root . --format jsonl --locale zh_CN --max-entries 80
python .codex/skills/auto-style-string-resources/scripts/check_string_constraints.py "正在处理 {count} 个文件" "正在处理 {count} 个素材"
```
