# Auto Style String Resources / 程序文案风格

<a id="触发示例与运行要求"></a>

## Prerequisites / 触发示例与运行要求

- 使用："审计这个仓库的 UI 字串，给出统一语气的候选"；"检查 i18n 文案和调用位置，保留占位符"。
- 不使用："翻译这句聊天消息"；"调整按钮颜色和间距"；"重构 JSON 配置键"。独立翻译、视觉布局和机器字段改造不属于文案资源审计。
- 两个辅助脚本仅用 Python 标准库。完整扫描能力需要 **Python 3.8+**：Python 字串识别依赖 3.8 起统一的 `ast.Constant` 节点；注解已延迟求值，不因 `list[str]` / `| None` 的写法单独要求 3.10。该下限来自代码与 API 核对，未在 3.8 解释器实测。扫描目标 Python 源码时，应使用能解析其语法的解释器，否则文件会被报告为解析失败。
- 本轮 CLI 烟测环境为 Linux x86_64、Python 3.12.14 / 3.13.5；macOS、Windows 未实测。脚本不依赖 shell 专用命令，按平台选择实际解释器路径，并使用能显示 UTF-8 的终端。没有 Python 时仍可人工审计，不能声称已运行脚本。

## Purpose / 目标

用于整理程序中的用户可见文字，包括按钮、标签、提示、空状态、警告、错误、导入/导出说明、README 和 docs。先审计资源与实际调用场景，再从用户输入、项目文档、较好的现有文案和真实使用场景归纳风格，按 `style_score` 和处理等级提出候选，并只在用户授权的范围内分批应用。

目标是让文字清楚、自然，像熟悉产品的人写给用户的话，同时贴合项目的受众与场景。不要为了统一语气或缩短句子而改变事实、确定性、必要条件、限制、警告和后果。代码或外部系统依赖的字段、占位符及其他契约必须保留。中文和日文都应按各自语言的自然习惯表达，不逐字套用另一语言的句式。

## Scope and Default Behavior / 适用边界与默认行为

- 用户只说“整理字串”“统一文案风格”“风格化 UI 文案”时：只做审计、归类、`style_score`、处理等级和 before/after 示例，不直接修改文件。用户明确要求修改且授权了范围时，按该范围执行；下列需要确认的保护项仍须先确认。
- 用户说“自动处理低风险项”时：只修改低风险且明确标记为“可自动改写”的字串。
- 涉及关键引导、费用/API Key、素材清理、隐私、文件覆盖、导入/导出、编译、知识库结构、错误恢复、模型调用、路径/命令/错误码、配置或持久化语义时：必须先给候选并等待用户确认。
- 多语言文案默认只展示用户当前交流语言对应的 locale；用户明确要求跨语言审计、翻译同步或指定 locale 时，才展示其他语言。根据项目实际映射识别 locale，不假定中文或日文一定使用某个文件名。
- 每轮只处理一个清晰批次；不要顺手混入 UI、逻辑、布局、架构、数据结构或依赖改动。

## 信息来源

按优先级读取并交叉验证：

1. 用户本轮给出的风格示例、禁忌和取舍。
2. 当前调用位置和功能语义，包括按钮、空状态、提示、警告、错误、状态、弹窗、导入/导出、编译和预览流程，以及文档的读者和用途。
3. 项目现有文案风格指南及实际存在的 README、架构说明、产品设计指南和相关稳定文档。
4. 现有较高质量字串，但不要把所有旧字串默认视为正确风格。
5. i18n 资源与对应 UI 使用位置；默认先看用户语言，其他语言只作为用户要求时的补充核对。

如果文档、代码和现有字串互相冲突，说明冲突并以当前代码和真实调用链为准；无法确认的事实或行为标为待确认，不凭文风猜测。

## 项目风格指南与文件组织

项目本地规范与中间产物统一放在 `.agent-workspace/`。先检查适用的 `AGENTS.md` 中的简短入口，再在 `.agent-workspace/design/` 定向查找文案指南，包括有权访问且可能被 Git 忽略的文件；不全盘搜索或遍历无关私密内容。发现多个适用候选且无法判断时，向用户确认。指南是项目参考，不覆盖用户本轮指令或实际功能语义。处理具体文案时只读取指南中相关章节，再核对本次涉及的调用位置；不因每次调用本技能而重新全仓扫描。

文案规范统一使用 `.agent-workspace/design/writing-guide.md`。首次没有指南时，结合本次范围分析项目现有文案、文档和用户偏好，提出精简内容；只有用户授权创建或更新指南时才写入，审计请求本身不自动授权写文件。项目可按需使用同目录下的 `ui-guide.md` 和 `resources.md` 分别记录界面规范和资源；它们不是必需文件，不默认生成重复规则，涉及本次文案时才参考。已有代码、产品文档和术语来源保持各自权威，指南引用入口而不复制维护同一规则。

发现旧目录、旧入口或已有指南尚未归位时，由 `yomihime-init` 先盘点并安全整理到 `.agent-workspace/`；本技能不自行迁移，也不建立旧路径的长期兼容、回退查找或双份权威。整理须保留已有指南内容，不自动覆盖目标或用户编辑；冲突先报告并确认，验证新位置和入口后再按授权收尾。迁移未完成时不新建重复指南，可依据本轮指令和实际文案完成不依赖该指南的审计，并说明缺口。已有文件只做授权范围内的定点更新，不因模板缺项而补写默认规则。

新指南记录适用范围、受众、语气、术语、各场景的强度、语言差异、必要约束及依据；只记录有证据且对后续工作有用的原则，不放密钥、个人隐私或无关敏感数据。当前生效的指南作为持久参考保留。临时树、候选表等中间材料放在 `.agent-workspace/<work-id>/scratch/`，例如 `string-tree.md` 和 `candidates.md`，标明是临时文件；完成后仅清理本次明确可清理的自建临时材料，不删除用户已有或用途不明的文件，也不删除指南。用户明确要求的正式文档或发布产物按指定目的地交付，不把本地中间文件自动当作交付物。

如用户授权修改 `AGENTS.md`，保留原有内容和结构，只在合适位置添加简短入口，指向实际指南路径，并说明存在时读取相关部分、缺失时参考现有文案并提示用户。不要把完整指南或一次性清单写入 `AGENTS.md`，也不设跨项目通用规则。未获授权时只建议入口，不修改该文件。若入口指向的指南缺失、不可读或路径失效，说明情况，按项目现有文案和本轮指令继续；不要声称已读取，也不要擅自重建或覆盖。

指南与本轮用户指令或当前代码冲突，或有可信证据表明某条已过时，应报告冲突并核实当前证据，不继续套用有冲突的旧规则，也不在未经授权时改指南。后续只在有具体证据表明用户偏好、产品用语或约束发生实质变化时，核对受影响章节并提出更新；文件时间或单个不同措辞本身不足以判定指南过时。经授权后局部更新并保留其他内容；不确定时询问，不静默重写。

`.agent-workspace/` 默认是本地工作区，不默认暂存、提交、发布或混入构建产物。检查指南和工作目录是否被 Git 忽略、是否未跟踪，以及项目的共享约定。被忽略或未跟踪的指南可能只存在于本地，不会随提交或克隆自动带到其他环境；向用户说明可移植性和隐私影响，不擅自更改忽略规则、暂存、提交或分享文件。保留用户已有共享约定；只有获授权且确认不含秘密或不应共享的信息后才按要求共享，不因目录约定擅自删除或取消跟踪原文件。

## 工作流

### 1. 扫描文字

先按上述方式查找指南，识别本次涉及的语言、框架、资源布局和文档位置，再用 `rg` 等工具定向定位。首次建立依据或用户要求完整审计时按实际范围扩大检查；已有可靠指南时只检查相关章节与本次范围，不重复全仓扫描。按实际范围覆盖：

- i18n 和其他本地化资源，以及标题、按钮、Label、ToolTip、菜单、状态、占位符、空状态、弹窗等硬编码 UI 文案。
- 后台代码中传入 UI、导出物、错误展示或用户可见报告的文本。
- README、docs，以及直接呈现给用户的 prompt、Markdown/HTML 模板和导入/导出说明。

区分用户可见文字和技术字串。不要把配置键、JSON schema 字段、持久化字段、测试断言、日志分类、命令片段、路径模板、错误码和协议字段当成普通文案处理。对既是用户可见内容又是机器契约的文本，先确认其用途与约束。

### 2. 构建使用场景树

先输出 UI/UX 字串树状图，而不是马上改写。树状图描述文字在用户体验中的使用位置，不是源码目录树。UI 按“页面 → 分组/区域 → 控件/流程 → 词条”分层；README 和 docs 可按读者任务、章节或使用流程另列分支。没有明确归属的项单列“待确认”。

例如，可按实际项目整理为“设置页 → 账户区域 → 保存按钮”“文件导入 → 覆盖提示”，以及“文档 → 安装 → 操作步骤”；这些仅为结构示例，不假定项目具有这些页面或功能。

节点优先使用用户能理解的概念；叶子可附类名、文件、行号或 i18n key。不要把源码目录直接当作主结构，除非确实无法确定其他归属。每个叶子用紧凑标签记录场景、控件或文档类型、位置、当前文本、资源或硬编码来源、多语言覆盖状态、占位符/插值、Markdown/HTML、快捷键、路径/命令/错误码及疑似技术字串。长解释另列到候选表。

可选脚本 `scripts/draft_string_tree.py` 的输出只是内部草稿，必须按实际使用场景重整、合并重复项、去除无关源码噪音并确认归属。它针对特定目录和 Python/PyQt 风格调用做启发式扫描，并非通用或完整索引；不要把未扫描到当作不存在，项目其他资源、语言和文档须另行检查。

### 3. 归纳目标风格并检查自然度

先从样本归纳，不预设旧文案都正确。说明哪些规则来自用户、哪些来自项目，简述受众、语气、信息密度、术语和风险场景的写法。短控件文本宜简洁，流程说明保留必要条件和后果；高风险场景应直白准确。项目气质来自当前项目证据，不预设某个产品的人设。

可用下列预设作为讨论风格的起点，也可按项目自定义。根据用户偏好和项目已有语气选择或组合，不强行套用；缺少依据时先给示例供用户选择。每种风格都随场景调整强度，按钮可简短，说明需完整，警告和错误应优先清楚准确。

- **实用简洁**：直说操作和结果，去掉不必要的铺垫。
- **清晰引导**：按用户的任务说明下一步，保留必要条件和结果。
- **轻松自然**：用平实、亲切的表达，不刻意卖萌或开玩笑。
- **主题化表达**：适度借用项目已有的主题、词汇和节奏，不妨碍理解。
- **日系轻柔**：语气克制、柔和，措辞留有余地，但不模糊事实、警告或责任；这只是语气选项，不绑定日语，也不凭文化印象强加人设或萌化表达。
- **项目自定义**：依据用户给出的样例和项目实际语气归纳原则。

中文和日文分别按各自的语言习惯、读者和使用场景写作与核对，不因选用预设自动翻译或同步其他 locale，也不虚构角色人设。可简要记录本次采用的风格原则供批次内参考；项目指南的创建与更新遵循上面的授权和文件组织规则。

逐条结合上下文检查是否清楚、自然、符合语言习惯：去掉没有实际作用的自我辩护、重复铺垫和生硬的模板式套话，避免空泛夸饰、机械排比和与场景不符的口吻。不要用禁词表机械替换，也不要根据措辞推断或归因于某个模型。解释限制、表达不确定性或提示真实风险时，保留有用内容，只改进其表达。中文和日文分别检查称谓、礼貌程度、语序和用词；不要为了显得亲切而夸大能力或承诺结果。

例如，普通按钮“点击此处进行保存操作”可根据实际操作简化为“保存”；日文按钮“保存を行います”可在合适场景简化为“保存”。但“保存可能失败，请先备份原文件”或“保存に失敗する場合があります。元のファイルをバックアップしてください”中的不确定性与备份提醒不能当作套话删除。示例不替代对实际行为的核实。

### 4. 打分与处理等级

逐条记录一个参考分数和一个处理等级，避免冗长的逐项评估。

参考分数使用单轴“可风格化程度”：

- 记为 `style_score`，范围 `0.0` 到 `10.0`，步进 `0.1`。
- `0.0` 表示应保持中性、准确、契约式表达，通常不适合拟人化或明显风格化；`10.0` 表示可明显承载项目语气、节奏和角色感。
- 此分数衡量风格发挥空间，不衡量原文的自然度或质量。低分文字仍可需要清晰、自然的候选表达，但必须保留语义并遵守对应风险等级；高分也不代表原文不自然或可以自动修改。
- 分数只用于排序和讨论，不等于自动修改许可。逐条表格只给数字；争议项、保护项或用户要求时，另作简短说明。

处理等级按上下文风险决定：

- 可自动改写：语义明确、技术约束少，通常是按钮、短标题、空状态短句、普通成功提示。
- 只给候选：语义重要或上下文稍复杂，提出 before/after 供用户选。
- 默认保护：高风险警告、密钥/费用/隐私/删除/覆盖/迁移/编译/导出兼容等文本，除非用户明确确认，否则不改；这类文本通常 `style_score` 较低。
- 只整理不改写：结构上需要迁移到 i18n、补全多语言或建立索引，但原文不应在本轮改变。
- 需要用户确认：风格方向、术语取舍、跨语言一致性或业务语义存在不确定性。

### 5. 生成审核样本

默认在改文件前给用户看不同处理等级的 before/after 示例，覆盖低风险可自动改写项、中风险候选项、默认保护项及必要说明、只整理不改写项，以及需要确认的术语或语气取舍。用户已明确授权直接修改的低风险范围，无需再次等待确认，可在完成后展示示例；默认保护项仍须先给候选并单独确认。

每个示例包含位置、场景、当前文本、候选文本、`style_score`、处理等级和保留的占位符/格式约束。常规项不写长理由；保护项、争议项和待确认项旁补充必要说明。候选应保留事实、条件、适用范围、程度、不确定性、真实风险和后果，不因文风更改功能承诺。

### 6. 分批应用

只有在用户授权范围内改文件。应用时：

- 严格限定在确认的文件、key、页面、模块或风险等级范围内。
- 保留所有占位符、插值变量、格式说明符、转义序列、Markdown/HTML 标签、快捷键标记、路径、命令、错误码和外部格式字段；文档中的链接目标、示例命令及事实也要核对。
- i18n 修改要维护项目要求的 locale 与 key 对齐；如只能可靠改一种语言，明确说明其他语言保持不变或需要后续人工确认，不凭猜测补译。
- 硬编码 UI 文案若适合迁移到 i18n，先把迁移列为“只整理不改写”或单独候选，不在文案风格批次中顺手改调用结构。
- 不调整控件结构、布局、信号槽、业务逻辑、线程、导出字段映射或知识库结构。

### 7. Validation and Reporting / 验证与汇报

修改后输出已改文件和范围、before/after 清单、每项 `style_score` 与处理等级、必要说明、跳过项及原因、已知风险和仍需确认的文案。常规低风险项不逐条写理由。

运行与修改相关的轻量检查，例如解析受影响的 JSON、检查链接与格式约束，并核对真实调用上下文；报告命令和结果。改动控件文案时，若能安全运行界面，检查受影响语言和状态下的换行、截断、溢出及可访问名称；无法检查时明确列为未验证。布局修复仍需符合原有授权范围。脚本不能证明语义、语言自然度或行为正确。

如改动影响长期文案规范、术语或 i18n 工作流，按上述规则提出或经授权更新项目指南及相关文档；仅在用户授权时修改 `AGENTS.md`。

## 输出格式建议

审计阶段使用“位置、场景、当前文本、style_score、处理等级、建议”的表格或紧凑分组。应用后提供“位置、Before、After、style_score、处理等级”。表格过长时按页面或风险等级拆分；完整清单可写入用户确认的临时审计文档，不要把大型一次性清单塞进 `AGENTS.md`。

## Available Scripts / 可选工具脚本

脚本只辅助初筛和约束检查，不能替代人工理解调用上下文。

- `scripts/draft_string_tree.py`：粗扫根目录 `i18n/*.json`、`i18n/*.jsonl` 和 `gui/`、`core/`、`utils/` 中的部分 Python 字串，推断页面与分组。它可能漏掉动态构造、其他路径、框架、语言和文档，也可能误报技术字串。`--locale` 按资源文件名筛选，可重复指定；不指定时扫描这些目录下的所有 locale。`source` 统一输出使用 `/` 分隔的项目相对路径，便于跨平台核对。输出必须人工核验。
- `scripts/check_string_constraints.py`：用正则比较常见占位符、HTML 标签、Markdown 链接、快捷键、路径和错误码。覆盖并不完整，可能误报或漏报；它比较匹配项及其出现次数，不验证位置参数的顺序，也不独立解析命令、转义序列或所有占位符语法。通过不证明所有契约或含义保持不变。

### Troubleshooting / 失败处理

- `draft_string_tree.py`：读取或解析失败时向 stderr 报告文件诊断和汇总，失败文件不输出候选；JSONL 按非空行解析 JSON，坏行报行号并拒绝该整个文件。退出码 0 表示扫描范围内完整成功（包括有效空项目），1 表示部分成功并输出成功文件候选，2 表示根目录错误或全部失败。非零退出码不能报告为完整审计；先核对诊断，再补查或修复输入。
- `check_string_constraints.py`：脚本报错时保护原字串并人工检查；检查通过也不代替上下文与语义核验。

### CLI Examples / CLI 示例

从技能安装目录调用脚本，例如：

```bash
python ~/.codex/skills/auto-style-string-resources/scripts/draft_string_tree.py --root . --format markdown --locale zh_CN --max-entries 80
python ~/.codex/skills/auto-style-string-resources/scripts/draft_string_tree.py --root . --format jsonl --locale zh_CN --max-entries 80
python ~/.codex/skills/auto-style-string-resources/scripts/check_string_constraints.py "正在处理 {count} 个文件" "正在处理 {count} 个素材"
```

示例中的 `zh_CN` 只是 locale 文件名示例，实际使用时按项目资源命名选择。脚本默认输出到终端；获准保存审计草稿时，使用 `.agent-workspace/<work-id>/scratch/` 下的新文件，不覆盖已有材料。
