# UI Design

## 目标与边界

以正在使用的界面为依据，整理可复用的项目设计指南；也支持从零设计和有明确范围的 UI 修复。先理解界面服务的任务，再处理视觉。**记录现状不等于批准改版**：已有项目默认保留既有视觉、布局、交互与功能；缺陷、冲突和改善想法单独标记为「建议」，不伪装成现状，不因建立指南而静默重绘界面。用户明确要求修改时，只在授权范围内实施；无关页面与依赖保持不变。

## 先找依据

1. 读取适用的 `AGENTS.md`，查找设计指南入口和项目约定；没有入口时，在有权访问的约定位置定向查找，包括可能被忽略的 local-dev 目录，不遍历无关私密内容。多个候选指南或归属不明时询问。找到适用指南后，先读取与本次任务有关的部分，再按需检查相关页面、样式、配置、组件库、设计 token 和主题；入口指向的指南缺失、不可读或路径失效时提示用户，参考实际 UI 继续，不声称已读取。
2. 对既有 UI，以用户提供的截图、可运行界面、组件及实际样式为证据，交叉核对有代表性的页面和状态。覆盖本次范围内的常态、悬停、焦点、禁用、错误、空态和窄窗口等；没看到的状态标「未核实」，不要猜。无法运行时读代码并明确限制，必要时请用户提供截图；未经许可不要启动会修改数据或触发外部操作的应用。
3. 区分设计意图与实现差异：记录可核验的颜色、字体、字号、间距、尺寸、圆角、边框、层级、组件状态、布局、图标、交互和平台约束，附简短来源（页面、文件或截图）；有冲突时列出具体位置及待确认项。不要从一个偶然值推断全局规则。已有指南过时或与当前代码冲突时说明并核实，不静默覆盖。
4. 如果项目已有规范、token 或主题机制，以实际维护它们的文件/系统作为权威来源；指南引用而不复制出另一套会漂移的值。若没有集中机制，可记录重复出现的实际值与位置，注明观察而非新规范；只有用户授权后才提议或建立 token。不要用文档值覆盖代码事实，也不未经批准迁移权威来源。

## 精简且持久的指南

优先沿用项目的文档和 local-dev 约定。没有指南时，先提出合适位置和精简内容；审计本身不授权创建或改写。明确授权创建/更新时，写到项目约定位置（例如项目已用 `.local-dev` 时可选 `.local-dev/design-guide.md`），不强制新建该目录。保留已有内容，只按授权做局部更新；不确定文件所有权或多个入口冲突时询问。指南应短而可维护，包含：适用范围与依据、界面目标、已观察到的规则、权威 token/组件入口、交互与可访问性约束、主题/平台差异、未核实项与明确分开的建议。不要把一次性清单、大量截图或完整源码塞进去。

仅在获准修改时，保留 `AGENTS.md` 内容与结构，加入一条简短入口，指向实际路径并说明按任务读取相关部分；指南不存在或不可读时参考实际 UI 并提示，不声称读过，不擅自重建。检查指南是否被 Git 忽略或未跟踪，说明它可能不会随克隆传播；不擅自更改忽略规则、提交或分享。指南和截图不应包含密钥、真实账户信息、个人数据或无关敏感内容，使用脱敏样本；不确定共享范围时先确认。

后续任务优先读取适用章节并核对实际实现，无需每次全仓扫描。有具体证据表明规范变化时报告，获得授权后只更新受影响章节。临时文件沿用项目工作目录；只清理本次创建且明确可清理的材料，绝不删除用户文件。

## 新项目与局部改动

- **新项目**：先确定目标用户、任务、平台、框架、内容密度、主要工作流、品牌与技术约束；缺少非关键细节时说明合理假设。提出有辨识度但适合用途的方向，并将待决定的设计和已实现的事实分开。用户授权实现后，从最重要的工作流建立小型 token、组件和状态，再逐步扩展；不要先引入庞大设计系统或依赖。
- **局部修复**：先重现并定位问题，比较相邻界面、组件和主题，选择最小修改；兼容现有规范和行为。若修复必须改变范围外的视觉或公共组件，说明影响并确认范围。不要把“优化 UI”当作重做整个产品的许可。
- **资源选择**：先用项目现有组件和资源。需要外部依据时按 `references/resources.md` 查官方文档，仅按当前问题选择；项目初始化如需取用资源，每次用户请求最多获取一个资源库，记录来源、版本或访问日期和实际文件的许可证，确认与项目兼容后再决定是否使用；软件、文档、字体、示例和第三方 registry 可能有不同条款。离线时用现有依赖和本地证据，说明未验证项；不要自动运行下载的脚本、示例或其他不可信代码，也不擅自安装依赖。

## 实用设计检查

根据任务选择原则，不套固定模板或禁用某种颜色：

- **层级与节奏**：让主要任务、当前状态和下一步显眼，次要操作退后；使用一致的间距、对齐与尺寸，避免靠装饰填满空白。视觉风格服务内容，可以克制也可以鲜明，但应有依据。
- **密集管理界面**：表格、筛选和批量操作优先可扫描性与稳定对齐；让关键列、排序、选择、状态与危险操作清楚可辨，支持溢出与小窗口，不靠牺牲可读性硬塞信息。
- **中日文及混排**：按实际字体覆盖与回退测试汉字、假名、标点、数字、英文及长文本；检查行高、换行、截断和缩放。不要假设所有汉字字形相同或凭文化刻板印象套风格；尊重系统与项目字体许可。
- **主题与无障碍**：核对亮/暗主题、系统设置及高对比度；文字和控件状态需有足够对比，不能只靠颜色传达。交互控件有可见焦点、语义名称、键盘顺序和适当命中区域；在平台适用时检查读屏、缩放和减少动画偏好。颜色、字号与对比度按适用标准和实际情况验证，不凭感觉宣布合规。
- **状态与反馈**：加载、空、错误、成功、禁用和破坏性操作都说明发生了什么和能做什么；保留用户输入、已有功能及风险提示。动效应有目的，不阻碍操作。

按需参考 `references/examples.md` 的例子；它们是思路，不是通用审美规则。

## 验证与交付

修改后运行项目已有的相关检查、测试和构建，能运行 UI 时在代表性窗口尺寸、实际主题及相关交互状态下截图或人工检查，与改动前比较；必要时检查键盘、缩放、中文/日文长文案与颜色对比。只在安全、授权的环境使用脱敏数据，不触发真实交易或破坏性操作。无法运行时列出未执行项和原因，不把静态检查说成视觉验证。

交付时说明证据与范围、现状和建议、已改文件、权威 token/组件来源、实际验证结果及未验证风险；建立指南时给出路径和 Git 可移植性。只做审计时给出可操作的发现与示例，不宣称代码已修改。
