# 按任务选择设计深度

## 先选架构，再选图

架构师先返回一个可核查的选择，而不是先产出一套图。任务包包含需求原文/来源、当前约束、范围与非目标、候选基准、相关证据入口、允许写入文件、交付终点和必要验收。复用已有主计划，不另开架构专属进度系统。

选择时只调查会改变本次决定的约束：

- 实际用户和规模、已有边界、团队职责及发布节奏。
- 本地/云端、单机/多实例、离线要求、平台与现有技术限制。
- 数据归属、事务边界、并发、时延、可用性、恢复与安全边界。
- 运维能力、迁移成本、可测性，以及下一次拆分需要什么证据。

优先能满足已知需求的最简单形式。例如小团队单一发布单元可采用有明确模块边界的单体；独立扩缩、故障隔离或组织边界有真实证据时再考虑服务拆分；存在外部扩展、隔离或宿主生命周期需求时才引入插件边界。不是统一规定任何项目采用这些形式，也不预建未来没有用户的扩展点。

在 `architecture.style` 与 `architecture.rationale` 记录选定形态和约束。只有真实争议才写 `alternatives`，说明未选原因；不为凑数量比较所有模式。缺少会改变方案的条件时标明假设/待决事项，关键产品取舍或权限由主调度者向用户确认，普通局部技术选择无需层层审批。

## 新项目：从骨架到可实施切片

1. 先确定系统边界、运行单元、主要模块职责、数据所有者与入口。只画能说明为何这样拆的总体视图，不能把不存在的模块标 current。
2. 选第一个可验收的纵向切片，展开对应模块和端到端流程，定义跨模块契约及失败路径。远期模块只保留必要边界，未知仍写 unknown。
3. 检查该切片是否可以独立实施和验收；在代码前解决关键接口/状态冲突。其余细节等后续切片成为当前工作时再展开。
4. 实现后用实际候选和验证证据更新受影响对象；代码存在与验收通过分开记录。

“先框架”是先明确最小关系和职责，不是先建通用框架、全套目录或全仓空壳。用户只要方案时止于方案，不自动实现。

## 已有项目：先现状，再本轮差异

1. 读取相关既有图纸、记忆和已变更文件，核对实际入口、调用、数据存储、测试与配置；基准包含影响判断的 staged/unstaged/untracked 内容。
2. 建立相关范围 as-is：哪些组件确实存在、接口当前怎样工作、证据覆盖到哪里。图纸与代码冲突时记录冲突并定点核查，不因旧文档或类型声明就假定运行行为。
3. 在同一源中增加/修改本轮所需 planned/proposed 对象和 `changes`，明确受影响接口、兼容性、数据迁移和回退条件；未变区域保留状态和原核验日期。
4. 仅展开本轮依赖。外部模块可以保留最小已知边界或 unknown，不要求把整个仓库“考古完成”才允许修复。

保留原有人工内容和当前有效决定。废弃旧图纸、搬迁规范源或改写项目记忆属于单独受管操作，不在“画新架构图”的名义下覆盖或删除。

## 架构师的交接与反馈

架构师返回：选择与理由、调查范围/基准、规范源路径和修订、当前切片的元素/契约/流程/变更 ID、证据、关键未知项及建议下一步。实现者返回产物、实际候选、验证结果和发现的契约冲突，不私自改公共契约后只更新自己的图。

公共边界变化由主调度者和唯一图纸 writer 协调，再将同一新修订通知受影响任务。小的只读调查不强制产生文件。多人写同一源时串行处理；Agent 身份、角色或 `decision: accepted` 都不扩展授权。必要独立评审只在真实独立执行后声称，不把一个 Agent 的自检说成独立审查。
