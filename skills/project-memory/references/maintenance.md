# 维护、归档与跨上下文恢复

## 恢复：按角色选择读取

主调度者或单 Agent 恢复时执行下列全文恢复流程。明确委派的普通子任务按 [知识交接与协作](collaboration.md) 读取任务包中的相关地图、约束与必要原始材料；记忆 writer 每批完整读取当前快照与待改文件。有效项目入口另有更广要求时先遵循并由主调度者协调，不能因本参考而忽略它。

1. 核实有效入口与作用域，遵循短入口，将当前快照作为第一份主动读取的记忆文件。全文读取；输出被截断则继续读完，不用搜索命中或摘要代替正文。
2. 从快照直接确认目标、有效约束、环境、实现与验证、阻塞及下一步，核对最新用户请求。正常恢复不读取 `archive/`，也不逐条重放旧目标/检查点来推导状态。
3. 核对相关区域的证据基准，比较自已核验 commit 以来的路径变化，加上 staged、unstaged 和相关 untracked 文件。仅比较 HEAD 会漏掉未提交实现；分支切换、改名或基准不可达时定点检查，不伪称已验证。
4. 接口变化连同直接依赖/调用方一起复核；未受影响事实保留原验证日期。采用标准 JSON 架构源时核对实际源路径、修订、相关对象及逐项状态；现状说明只归并证据确认的事实，不复制完整契约或把目标状态当实现。只有证据表明边界整体变化或用户要求全面调查时，才扩大扫描。
5. 核验本次所需环境、连接、授权和工具能力；保留资源身份，不用历史离线记录跳过实际探测。不要把“本机通过”改写成“目标环境通过”。
6. 给出具体下一步与仍未验证的条件，继续已获授权工作。快照和历史都不是自动执行旧命令的许可。

快照缺失或明显不完整时，明确说明缺口，先按最新请求和现有证据安全继续。首次开工或发现旧布局时，交 yomihime-init 盘点并安全整理；若获准维护，再按整理后的证据补齐 `.agent-workspace/memory/current.md`。不要把旧目录回退或每次读取全部历史设为永久恢复流程。只读模式仅报告缺口。

## 什么时候写

在用户确定目标/约束、架构边界有实质变化、发现可靠调试入口、根因被证实、回归验证完成或阶段交接时维护。没有实际信息变化不重写；不必每次工具调用都写，也不依赖预测上下文压缩时机。角色回报先经主调度者接收，按有来源的事实批次归并，不能把猜测或旧消息自动变成新决定。

调查可以增量进行，输出必须仍是完整当前快照：新结论更新受影响部分，其他有效事实保留；删去被替代内容和无关过程，不生成只含“本轮变化”的新快照。

## 每次改写：先归档，再更新

1. 先通过隐私与加载检查，确定本批受管文件和已有人工内容。完整读取当前快照及所有待改文件，记录原内容校验值；单一写入者负责同一批文件。可将写入权交给明确范围内的记忆维护员，交回前其他角色不同时改这批文件。只读模式不执行以下写入。
2. 在内存或获准的临时位置拟好完整新快照及必要入口调整，核对有效事实、来源、日期、证据覆盖、未知项和下一步。保留无关人工内容；只让必要的稳定约束进入短入口。
3. 替换前重新核对原内容，发现用户或其他 agent 已修改则重新读取、协调并重建草稿，不能覆盖新内容。没有内容变化的文件不改、不归档。
4. 为整批变更创建唯一归档目录；在覆盖任何既有文件前，先原字节复制全部受影响旧文件，保存来源路径和校验值清单，再逐一验证归档与读取基线一致。归档失败、发现秘密或并发变化时，不开始覆盖受影响文件，遵循隐私边界解决；不能用脱敏后副本声称保存了原版。
5. 全部归档验证成功后，再替换当前快照及必要的受管文件；写入前再次核对原内容。新文件没有旧版，清单中标注新增。保留旧版归档，不覆盖既有归档目录。
6. 验证新文件内容、路径、入口与快照一致性和隐私排除，检查没有混合新旧状态。若部分写入失败，明确记录受影响路径，先完成一致性修复；必要时从本批归档恢复，不能覆盖并发人工编辑，也不能报告更新完成。回执给出批次、纳入来源、旧/新校验值、归档位置、核验和未纳入项，交回写入权；细则见协作参考。

内容重排、精简、入口改写和旧结构迁移同样先归档。日期用于说明证据鲜度，不能把今天的快照更新时间盖到未复核事实上。分别表述“实现了”“测试通过”“实际运行通过”“目标环境验证通过”。

证据固化与地图更新遵循 [知识交接与协作](collaboration.md)。旧报告与新决定冲突时保留来源和待核实项，不回退新状态；候选变化时只复用仍有效的证据。固化源未稳定、秘密/隐私冲突、归档失败或并发变化时保留来源，不清理它来制造完整交付。

采用 architecture-design 并确认 JSON 权威后，架构源由其获准的唯一 writer 跨任务维护；记忆 writer 更新 `memory/references/architecture.md` 的有证据现状及源引用，不另造 JSON 或改写源中的契约。`.agent-workspace/architecture/` 供按需新建稳定源，既有有效源原位复用；迁移或覆盖须另有覆盖该动作的授权、旧版保存与引用核验。图纸入口仍指向实际权威源，不能只改链接而留下缺失或多份活跃源。

## 接收初始化整理的旧材料

旧项目的目录盘点和安全整理由 yomihime-init 在下次开工时负责，本 Skill 接收其已确认的记忆材料与来源映射，维护唯一 `.agent-workspace/memory/`。不在普通恢复中自动搜索旧目录，不建立别名、链接回退或双写。仅处理已获授权的记忆范围，不为了套模板重排用户文档，也不改其他仓库或全局记忆。

1. 按 yomihime-init 的已核验清单一次性完整读取旧目标/决定、检查点及相关地图、环境、故障、资源等受管文件，辨认仍有效的工程事实、用户决定及证据；检查新结构中已有内容，不因目标路径相同覆盖另一份材料。无法确认的冲突或缺口明确标未核实。
2. 将这些现行事实合并成单份完整快照，保留原来源、适用范围和验证日期。旧的沿革与过程不混进新正文，也不把所有事实重新标成已验证。
3. 按整批归档流程保存所有要改写或迁移的旧文件，包括需要修改的有效入口；确认归档可恢复后再写新快照、更新读取指令。
4. 目录迁移按 yomihime-init 的授权范围和恢复清单执行，人工或无关文档保留；没有迁移授权时只交盘点结果。需暂时保留的旧源不再作为日常状态入口，来源、未处理冲突和引用缺口明确记录。检查有效 AGENTS/override 与相关恢复指令，在获准范围内更新为新快照入口，不自行忽略仍有效的指导。
5. 通过入口与新快照即可恢复当前工作；旧资料可在归档精确找回。尚有有效入口未能更新或快照缺项时报告迁移未完成。

## 精简与历史追溯

- 当前文件只保留有效约束、现行方案、仍有用的调试结论及证据；失效内容在改写前已归档，不将旧决定沿革留在正文。
- 详细源码与原始日志引用稳定路径；恢复必需的现行结论仍直接写入快照。
- 仅在明确追溯原因、审计或找回旧证据时按来源/日期定向读取归档；先核实其现在是否仍成立，再决定是否写回现状。
- 归档默认保留，不自动清理历史；删除和保留期限调整需要既有明确授权。
- 活跃架构源、现状说明及仍被引用的图纸依据不按任务结束自动清理；派生网页也先核对源可重建、引用与清理授权，不能用删除旧源制造唯一性。
- 定期检查路径、鲜度与隐私排除；只读操作只给建议，不维护文件。

## 交接验证

针对本次变更做隔离合成工程验证，不复制真实私有记忆或真实环境快照。让不了解先前对话的独立实例只拿当前任务、通用 Skill 和最少合成材料，观察实际行为与产物，而非只匹配关键词。

按受影响行为选取场景：只凭当前快照恢复而不重放历史；普通子任务只读相关知识仍可定点工作；材料不足或地图过期时补具体缺口；维护后有效事实仍完整、被替代事实仅存归档；旧版字节和批次清单可核验；旧报告不回退新决定；证据固化后引用可达；旧结构迁移后没有双重入口；归档失败或并发修改时不覆盖；只读检查零写入。隐私与加载规则有变化时，补查 tracked/staged 冲突、同层 override、人工指导保留等相关行为。

报告哪些是文档/路径检查、哪些是隔离行为验证、哪些在真实客户端实际验证；不得将模拟恢复描述为真实自动加载或压缩恢复保证。
